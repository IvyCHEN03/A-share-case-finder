# 条件强度与最少追问规则

## 目标

在不误解业务口径的前提下减少无效追问。不要把Skill变成逐项填写的问卷，也不要用未经说明的假设替用户作出会改变结论的选择。

## 一、条件强度

| 强度 | 常见措辞 | 对严格资格的影响 | 默认动作 |
|---|---|---|---|
| hard | 必须、仅限、只接受、同时满足、排除 | 决定案例能否进入A类 | 直接纳入必要条件 |
| preferred | 最好、优先、尽量、倾向于 | 不影响A类资格，只影响排序 | 声明假设并优先检索 |
| fallback | 可以参考、类似亦可、找不到可放宽 | 仅进入近似案例范围 | 严格检索后再展开 |
| unresolved | 前后矛盾、指代不明、无法识别“且/或” | 取决于具体歧义 | 判断是否阻塞 |

否定词优先于语气词。例如“最好不要包含终止项目”默认是preferred排除；“不要包含终止项目”是hard排除。

## 二、是否追问

仅在同时满足以下条件时暂停并问一个问题：

1. 条件为unresolved，或用户要将preferred条件用于正式论证但其强度不明确；
2. 不同解释会改变严格案例集合、监管命题或最终结论；
3. 无法通过同时检索两套口径低成本覆盖；
4. 现有上下文不能合理推断用户意图。

其余情况不阻塞。先说明采用的解释，并继续检索。

## 三、推荐表达

### 非阻塞假设

```text
我先将“无实际控制人”作为优先条件：第一层检索无实控人案例，有实控人的相似案例仅作为备选并单列。若你只接受无实控人案例，我会将其升级为硬性条件。
```

### 阻塞问题

```text
这里需要确认一个会改变严格结论的口径：你是只接受无实际控制人的发行人，还是希望无实控人优先、找不到时也接受有实控人的近似案例？
```

一次只问最关键的一项；不要同时发送板块、时间、状态、阈值等一长串问题。

## 四、典型判断

| 用户表达 | 处理 |
|---|---|
| “必须是无实控人” | hard；有实控人案例为C |
| “最好是无实控人” | preferred；无实控人优先，有实控人可保留但靠后 |
| “找不到的话，有实控人的也可以” | 无实控人为hard第一路径，有实控人为fallback第二路径 |
| “证明无实控人公司也能存在该安排，最好找成功上市案例” | 无实控人是论证前提，按hard处理；成功上市为preferred，除非上下文要求上市成功先例 |
| “共同签协议或者表决权委托都可以” | OR；拆成两条独立检索路径，不追问 |
| “直接或间接都行，但不要通过实控人归集” | direct/indirect均可；“不通过实控人”是hard排除 |

## 五、口径变化

用户确认、收紧或放宽条件后：

1. 新建S版本；
2. 记录条件从preferred/fallback/unresolved变为hard，或反向变化；
3. 重评全部候选，而不是只调整新案例；
4. 解释评级变化来自匹配口径，而非证据强弱变化。
